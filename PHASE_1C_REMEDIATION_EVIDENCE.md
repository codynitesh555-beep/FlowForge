# Phase 1C Remediation Evidence Report

**Purpose:** evidence package for a fresh independent audit. This report reads the original audit and remediation record, then checks the current implementation, selected tests, and six project documents. No tests, builds, database commands, Prisma CLI, migrations, Docker commands, or database connections were run for this report. The verification counts below are copied from the existing remediation record, not independently reproduced.

## Executive summary

The remediation made concrete changes: post-write absence now throws instead of returning success-like `null`; project archive releases active assignments and writes removal history; duplicate/FK errors are translated at selected persistence boundaries; and Graph Engine diagnostics are logged safely while API responses omit subcodes. It also added tests that call real `PrismaProjectTaskStore` methods with fake transaction clients.

The new tests demonstrate selected application control flow and that callback failures propagate. They do **not** simulate rollback of database state: the fake `$transaction` sets `rolledBack = true` but does not restore state, and root and transaction Prisma delegates alias the same objects. The tests also do not cover every mutation, all tenant predicates, exact graph-revision counts, or actual PostgreSQL locking/constraint behavior. The reported offline suite/build results are documentary evidence only in this pass.

**Recommendation: READY FOR INDEPENDENT RE-AUDIT.** This means an independent reviewer can review the remediation and its limitations. It does not mean Phase 1C passes, and it does not authorize database testing. PostgreSQL/client compatibility and real transaction, lock, index, and isolation behavior remain unverified.

The harness at `:35-97` is a deliberately narrow fake. It uses `Prisma.Sql` objects for string/value inspection, but no real Prisma transaction, pool, SQL execution, savepoint, or rollback. Its `rolledBack` flag is set whenever the callback throws, while `committed` is set on callback resolution. It does not snapshot or undo calls/state. Therefore “rollback” in test names means **callback rejection / no fake commit flag**, not proof of PostgreSQL rollback.

## Requested implementation checks

### `updateTask` and `softDeleteTask`

- `updateTask` checks current version and assignment authorization, performs a tenant/project/task/deleted/version-scoped `updateMany`, requires exactly one row, and throws `PERSISTENCE_INVARIANT_VIOLATION` if the post-write read is absent (`prisma-project-task-store.ts:292-335`). The absent-read branch is directly tested at spec lines 101-110.
- `softDeleteTask` uses the same scope/version check, releases active assignments and emits their removal events, increments graph revision, then throws on absent post-write task read (`:338-371`). The absent-read branch is tested at spec lines 127-140, but the test supplies no assignment rows. The non-empty assignment release/event path is exercised by archive tests, not by task deletion.
- No real rollback was demonstrated. The production code passes the callback to Prisma `$transaction` via `withTransaction` (`src/infrastructure/database/transaction.ts:8-10`), but database rollback semantics are PostgreSQL-only evidence.

### `archiveProject`

- Code selects scoped active assignment rows with `ORDER BY id ASC FOR UPDATE` and releases them using scoped Prisma `updateMany`; exact count is enforced (`prisma-project-task-store.ts:217-251`). Removal events and the first archive event use the same `transaction` argument via `writeProjectDomainEvent` (`:45-68`). The archive path does not increment graph revision, consistent with assignment-only changes not affecting graph structure.
- Fake tests cover normal release/event calls, repeated-archive repair, count mismatch rejection, and an event failure. They do not prove database state rollback or lock behavior.
- `unassignTask` still requires a writable project (`:507-516`). The new archive cleanup is intended to ensure no active assignments remain after archive; repeat archive repairs residual rows. This assumption must be checked against persisted pre-remediation data and real concurrent transactions.

### Graph, tenant predicates, and locks

- Writes obtain organization `FOR SHARE`, then memberships scoped to the organization and locked in ID order (`prisma-project-task-store.ts:70-87`); project lock then obtains advisory key before tenant-scoped project `FOR UPDATE` (`:90-101`). Identity lifecycle takes organization `FOR UPDATE`, memberships ordered by ID, then assignment IDs ordered (`src/modules/identity/infrastructure/prisma-membership-lifecycle.ts:19-37`, `:69-83`). Code inspection indicates a consistent organization gate; no lock race or deadlock was executed.
- The active graph reads tasks by project+organization and dependencies by project+organization (`prisma-project-task-store.ts:142-161`); the pure adapter excludes deleted tasks, removed edges, and edges touching deleted tasks (`src/modules/projects/scheduling.ts:16-34`). Scheduling entry acquires the advisory/project locks before graph reads (`prisma-project-task-store.ts:374-386`).
- Routes resolve active principal from the authenticated user and organization path; app-service/store receives organization scope from that principal. Exact route check is at `src/api/project-task-routes.ts:65-75`; schema composite relations are at `prisma/schema.prisma:97-154`. The new adapter tests only sample the org lock and one update predicate; tenant safety of all DB predicates/FKs remains unverified at runtime.

### Transaction propagation and event writes

- All mutation callbacks inspected enter `withTransaction` and use their `transaction` parameter for model/raw writes. `writeProjectDomainEvent(transaction, ...)` writes actor snapshot, ActivityLog, and OutboxEvent through that parameter (`prisma-project-task-store.ts:45-68`). `unassignTask` does a scoped pre-read on the root client only to identify a membership lock (`:507-511`), then re-reads/locks and writes within the transaction (`:512-534`). Read-only list/get methods use the root client as expected.
- Source inspection supports client propagation. Tests demonstrate selected callback paths but do not detect an accidental root-delegate call in general because fake root and transaction delegates alias at spec lines 78-91. No statement here proves actual transaction behavior.

### Graph revision rules

- Increment callsites: task create `:269`; task update only if PERT values changed `:329`; task soft-delete `:365`; dependency add `:430`; dependency remove `:455`. Project metadata/archive and assignment create/remove paths have no increment call (`:199-251`, `:475-535`).
- The new tests inject graph-revision failure and check callback rejection, but do **not** assert exactly one successful increment per graph mutation or zero increments for assignment-only mutation. This remains a material offline coverage gap; PostgreSQL checks are also required for actual behavior.

### Duplicate constraints and optimistic versions

- Unique/FK helper recognizes Prisma `P2002`/`P2003` and raw `P2010` with SQLSTATE `23505`/`23503` (`prisma-project-task-store.ts:113-123`). Dependency insert maps unique/FK violations to `DEPENDENCY_EXISTS`/`TASK_NOT_FOUND` (`:416-429`); assignment creation maps to `ASSIGNMENT_EXISTS`/`TASK_NOT_FOUND` (`:489-496`). Tests inject these shapes (`prisma-project-task-store.spec.ts:272-306`). Actual provider error metadata remains unverified.
- Stale task version is checked before write and again in the scoped update predicate (`prisma-project-task-store.ts:298-326`; soft delete `:344-352`). Adapter test covers stale-before-write (`spec.ts:241-247`); API test covers mocked service conflict mapping (`src/api/app.spec.ts:151-166`). Concurrent stale updates need PostgreSQL verification.

## Remaining gaps and regression risks

1. Fake `$transaction` behavior does not prove commit/rollback semantics; no database transaction rollback was verified.
2. Root and transaction delegates alias in the test harness, so propagation is source-inspected, not regression-tested against a root-client misuse.
3. No success-path tests assert exact graphRevision increment counts or assignment-only zero increment. Dependency removal and unassignment adapter paths are not directly exercised.
4. Soft-delete test has no active assignments; task-delete assignment release/event handling is not directly tested (archive tests do exercise assignment release under archive).
5. Lock test checks only partial order; it does not assert membership-before-advisory ordering, all row locks, or deadlock outcomes.
6. Tenant test checks early stop on absent organization and one parameter binding, not a cross-tenant row fixture for every read/write path or actual composite-FK enforcement.
7. Graph API test uses a mock service and test logging is disabled by `nodeEnv: 'test'`; safe subcode logging is source-inspected, not asserted.
8. Unique/FK mapping tests inject guessed Prisma/SQL error shapes. Actual Prisma 7 / `pg` adapter metadata for the migration’s partial indexes is not verified.
9. Generated Prisma Client/schema compatibility, migration replay, SQL column names against PostgreSQL, FK/partial-index enforcement, trigger arithmetic, isolation, races, and schedule consistency remain unverified.
10. The six docs contain the roadmap/frontend inconsistencies noted above.
